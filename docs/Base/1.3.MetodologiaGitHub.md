# Metodologia de Trabalho no GitHub

## Descrição

Esta página documenta como o Grupo 04 utilizou uma sprint, um quadro Kanban e os recursos do GitHub para organizar e rastrear a Entrega 01.

## Objetivo

Registrar a organização do trabalho, desde o planejamento até a integração dos artefatos, relacionando reuniões, issues, commits, pull requests e páginas publicadas.

## Metodologia

A Entrega 01 foi organizada como uma **sprint de duas semanas**, iniciada na [primeira reunião geral, em 14/08/2026](/Atas/AtaGeral01.md), e encerrada com a entrega de 28/08/2026. Dentro desse período, o grupo utilizou um **quadro Kanban no GitHub** para visualizar as tarefas e acompanhar seu andamento.

O Kanban foi utilizado para organizar o fluxo de trabalho, enquanto a sprint definiu o intervalo da entrega. Para o versionamento, adotou-se um fluxo inspirado no GitHub Flow: cada alteração era desenvolvida em uma branch e integrada à `main` por pull request.

Renan Pereira Reis e Marcos Vinícius Gündel da Silva ficaram responsáveis pela criação e pela organização inicial das issues. Outros integrantes puderam registrar atividades complementares quando necessário, como a issue da Ata 01 do Subgrupo 01.

O quadro Kanban possuía cinco colunas: `Backlog`, para atividades ainda não priorizadas; `Ready`, para atividades prontas para começar; `In Progress`, para o trabalho em execução; `In Review`, para as entregas em revisão; e `Done`, para as atividades concluídas.

## Fluxo de Trabalho

```text
Reunião ou necessidade identificada
                 ↓
       Issue no quadro Kanban
                 ↓
     Branch e commits incrementais
                 ↓
        Pull request e revisão
                 ↓
       Integração na branch main
                 ↓
     Publicação e fechamento da issue
```

<p align="center">Figura 1: Fluxo de trabalho adotado pelo Grupo 04. Fonte: processo da equipe, 2026.</p>

O processo foi aplicado da seguinte forma:

1. As reuniões e as diretrizes da disciplina definiam as atividades da sprint.
2. As atividades eram registradas em issues e acompanhadas no quadro Kanban.
3. Cada contribuição era desenvolvida em uma branch temática e registrada em commits.
4. O pull request reunia o resultado, a issue relacionada e as verificações realizadas.
5. Após a revisão, a alteração era integrada à `main` e publicada no site.

## Definição de Pronto

Uma atividade era considerada concluída quando:

- atendia às tarefas e aos critérios de aceitação da issue;
- preservava os arquivos e as evidências necessárias;
- possuía links, mídias, legendas e histórico de versão verificados;
- atualizava a participação dos responsáveis, quando aplicável;
- era revisada e integrada à `main` por pull request.

## Avaliação Crítica

O uso conjunto de sprint, Kanban e GitHub permitiu dividir o trabalho entre as subequipes, acompanhar tarefas e manter uma cadeia verificável entre decisões e entregas. Issues, commits e pull requests também facilitaram a identificação das contribuições individuais.

Parte das issues foi criada depois que algumas atividades já haviam começado, reduzindo seu valor para o planejamento inicial. Para os próximos ciclos, recomenda-se registrar as tarefas no início da sprint, manter o quadro atualizado durante a execução e automatizar verificações de links e formatação.
